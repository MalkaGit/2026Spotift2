## Node → Cloud → Microservices Learning Plan (Spotify app)

You’re a C# backend dev becoming a **senior Node/REST/DB engineer** using a Spotify-like app.

Each step below tells you:

- **Goal** (what you learn)
- **User story** (what the user does)
- **On screen** (what you see)
- **API endpoints** (what you build / test)
- **CV line** (how to phrase it)

You can stop after certain phases and already have strong CV bullets (this is called out along the way).

---

## Phase 1 – Backend Foundation (Node, MySQL, Docker, Testing, Search, Transactions, Albums/Playlists, First Deploy)

### 1. Run everything with Docker

- **Goal**: Run Node API + MySQL with Docker Compose (no manual DB setup).
- **User story (developer)**:  
  *As a developer, I can start the whole app (API + DB) with one command so I can focus on features instead of environment problems.*
- **On screen**: Same app as now, but it runs via `docker compose up`.
- **API endpoints** (already exist, you only ensure they work in Docker):
  - `POST /auth/register`
  - `POST /auth/login`
  - `GET /me/profile`
  - `GET /me/likes`
  - `POST /me/likes`
  - (Optional) `GET /search/artists?q=...` – current search
  - (Optional) `GET /health` – simple healthcheck.
- **CV line**:  
  **"Containerized Node/Express API and MySQL with Docker Compose for consistent local environments."**

---

### 2. Automated API tests (integration)

- **Goal**: Use Jest/Vitest + Supertest to cover your main flows end-to-end.
- **User story (developer)**:  
  *As a developer, I can run `npm test` and get confidence that register, login, likes, and search still work after code changes.*
- **On screen**: Terminal: green tests; no UI changes.
- **API endpoints to cover**:
  - **Auth**:
    - `POST /auth/register`
    - `POST /auth/login`
  - **Profile**:
    - `GET /me/profile`
  - **Likes**:
    - `POST /me/likes`
    - `GET /me/likes`
    - (Optional) `DELETE /me/likes/:id`
  - **Search (current v1/v2)**:
    - `GET /search/artists?q=...` (or your current routes)
- **Scenario example**:
  - Register → Login → Add like → Query likes → Assert DB and response.
- **CV line**:  
  **"Implemented integration tests for Node REST API using Jest/Vitest and Supertest (auth, profile, likes, search)."**

---

### 3. Unified search v1 – single endpoint, MySQL FULLTEXT

- **Goal**: One **unified search** endpoint that returns artists and tracks (and later albums) using MySQL FULLTEXT.
- **User story (end-user)**:  
  *As a user, I can type in one search box and see both artists and tracks (and optionally albums) in one result list.*
- **On screen**:
  - In the UI search page: sections like **Artists** and **Tracks** under a single search box.
- **API endpoints**:
  - `GET /search?q=<query>&type=<artists|tracks|albums|all>`
    - Response example:
      ```json
      {
        "artists": [],
        "tracks": [],
        "albums": []
      }
      ```
  - **DB**:
    - Table `searchable_entities` (or separate FULLTEXT indices on `artists` and `tracks`).
- **CV line**:  
  **"Designed a unified search API with MySQL FULLTEXT, returning artists and tracks from a single endpoint."**

---

### 4. Transactions – delete artist / playlist with cascades

- **Goal**: Learn **transactions** to keep data consistent when deleting.
- **User story (admin/user)**:  
  *As an admin/user, when I delete an artist or playlist, I never see broken likes or orphan playlist tracks.*
- **On screen**:
  - After delete: no broken references in “Liked Songs” or playlists.
- **API endpoints**:
  - `DELETE /artists/:artistId`
    - Transaction: delete artist + all likes that reference that artist (and optionally tracks, albums).
  - `DELETE /playlists/:playlistId`
    - Transaction: delete playlist + all rows in `playlist_tracks`.
- **Test scenario**:
  - Create artist, tracks, likes, playlists with tracks.  
  - Delete artist or playlist.  
  - Check likes / playlist_tracks tables and responses (no broken rows).
- **CV line**:  
  **"Implemented transactional deletes in Node/Express with MySQL to cascade removal of likes and playlist tracks."**

---

### 5. Albums + Playlists (domain modeling)

- **Goal**: Extend domain so you handle **albums** and **playlists** like Spotify.
- **User story (end-user)**:  
  *As a user, I can like albums, view tracks in an album, create/rename playlists, and add tracks or whole albums to my playlists.*
- **On screen**:
  - Album page: album details + tracks.
  - Playlist page: playlist name + track list.
  - Buttons: “Like album”, “Create playlist”, “Rename playlist”, “Add to playlist”.
- **API endpoints**:
  - **Albums**
    - `GET /albums/:albumId`
    - `POST /me/albums/:albumId/like`
    - `DELETE /me/albums/:albumId/like`
  - **Playlists**
    - `POST /me/playlists` – create playlist
    - `PATCH /me/playlists/:playlistId` – rename
    - `GET /me/playlists` – list my playlists
    - `GET /me/playlists/:playlistId` – details + tracks
    - `POST /me/playlists/:playlistId/tracks` – add single track
      - body: `{ "trackId": "..." }`
    - `POST /me/playlists/:playlistId/tracks/bulk` – add multiple tracks (e.g. full album)
      - body: `{ "trackIds": ["...","..."] }`
- **CV line**:  
  **"Modeled albums and playlists in MySQL and built REST endpoints for album likes, playlist CRUD, and track assignment."**

---

### 6. Unified search v2 – Elasticsearch (same API, better engine)

- **Goal**: Migrate unified search to **Elasticsearch** without breaking the API.
- **User story (end-user)**:  
  *As a user, search behaves the same but remains fast and relevant as the catalog grows.*
- **On screen**:
  - Same search page and layout; improved relevance/typo tolerance is invisible but real.
- **API endpoints** (same contract as Step 3):
  - `GET /search?q=<query>&type=<artists|tracks|albums|all>`
  - Optional admin tools:
    - `POST /admin/search/reindex` – rebuild ES index from MySQL.
- **CV line**:  
  **"Migrated unified search from MySQL FULLTEXT to Elasticsearch, preserving API contract while improving scalability and relevance."**

---

### 7. Optional: MongoDB for user preferences

- **Goal**: Learn using a **second data store** (Mongo) for non-critical data (preferences).
- **User story (end-user)**:  
  *As a user, I can change app preferences (theme, default view) and the app remembers them next time I log in.*
- **On screen**:
  - Settings/Profile page with theme and default view.
- **API endpoints**:
  - `GET /me/preferences`
  - `PUT /me/preferences`
    - body: `{ "theme": "dark", "defaultView": "library" }`
- **CV line**:  
  **"Integrated MongoDB alongside MySQL to store user preferences while keeping relational data in MySQL."**

## Phase 2 – Cloud Fundamentals (AWS first, then OCI)

### 9. AWS config & secrets (Parameter Store + Secrets Manager)

- **Goal**: No secrets/config in code; use AWS services correctly.
- **User story (developer)**:  
  *As a developer, I can configure DB host, S3 bucket, and queue URLs via AWS Parameter Store and Secrets Manager so that no secrets live in code.*
- **On screen**:
  - No UI change; your app still runs, but config is now loaded from AWS.
- **API behavior**:
  - On startup, server reads:
    - DB host, queue URL, S3 bucket name from **SSM Parameter Store**.
    - DB password, `JWT_SECRET` from **Secrets Manager**.
- **CV line**:  
  **"Used AWS SSM Parameter Store and Secrets Manager for config and secrets (DB, JWT), with IAM roles instead of access keys."**

---

### 10. S3 for album art / artist images

- **Goal**: Use S3 for binary assets with URLs in MySQL.

## Phase 3 – Modular Monolith (Stepping Stone to Microservices)

### 13. Domain boundaries + internal API gateway

- **Goal**: Structure monolith into clear modules.
- **User story (end-user)**:  
  *As a user, nothing changes visually; the app continues to work while the backend gets cleaner and more maintainable.*
- **On screen**:
  - No change; login/search/likes/playlists still work.
- **Internal structure**:
  - Modules:
    - `users` (auth, profile)
    - `catalog` (artists, albums, tracks, search)
    - `engagement` (likes, playlists, plays)
  - Express routes:
    - `/api/users/...`
    - `/api/catalog/...`
    - `/api/engagement/...`
- **API endpoints**:
  - Same URLs as before, but internally grouped by module.
  - No cross-domain joins (e.g. engagement does not directly join to catalog tables).
- **CV line**:  
  **"Refactored Node monolith into a modular architecture with clear domains (users, catalog, engagement) behind a single API gateway."**

---

## Phase 4 – Microservices (Split & Run)

### 14. Split into services + simple gateway

- **Goal**: Turn your modular monolith into 2–3 microservices.
- **User story (end-user)**:  
  *As a user, I still log in, search, like tracks, and use playlists through one URL, but behind the scenes the app runs as multiple services.*
- **On screen**:
  - Same UI and URL; architecture changed only on the backend.
- **Services** (example):
  - `auth-users` – register/login/profile, owns `users` table.
  - `catalog` – artists, albums, tracks, search (with ES), owns catalog tables.
  - `engagement` – likes, playlists, plays, owns engagement tables.
- **API endpoints** (seen by client; routed by gateway):
  - `/api/auth/register`, `/api/auth/login`, `/api/me/profile` → `auth-users`
  - `/api/search`, `/api/artists`, `/api/albums`, `/api/tracks` → `catalog`
  - `/api/me/likes`, `/api/me/playlists`, `/api/play` → `engagement`
- **Gateway**:
  - Could be a Node/Express proxy or Nginx: routes path prefixes to service URLs.
- **CV line**:  
  **"Split monolith into microservices (auth, catalog, engagement) with separate databases, Docker images, and an API gateway/proxy."**

> **After Phase 4 you can additionally say**: “Designed and implemented a microservices architecture.”

## Phase 5 – Message Queues (Real Use: Plays)

### 15. Play events → SQS → worker

- **Goal**: Use SQS for real async work (not just demo).
- **User story (end-user)**:  
  *As a user, when I press play, playback is instant and play counts are updated in the background.*
- **On screen**:
  - “Play” works smoothly; you may see play count increase after refresh or small delay.
- **API endpoints**:
  - `POST /play`
    - body: `{ "trackId": "...", "device": "web" }`
    - API sends `{ userId, trackId, playedAt, device }` to SQS.
- **Worker**:
  - Node worker (or separate service) that:
    - Reads from SQS.
    - Updates `track_plays` table or `play_counts` aggregate.
- **CV line**:  
  **"Integrated AWS SQS and a Node worker to process play events asynchronously, decoupling API requests from analytics writes."**

## Phase 6 – Analytics (Popularity, Play Counts)

### 16. Play counts + popularity

- **Goal**: Turn raw play events into **product features**: counts and popularity.
- **User story (end-user)**:  
  *As a user, I can see how many times tracks were played and which tracks/artists are most popular.*
- **On screen**:
  - Track rows show `123,456 plays`.
  - Artist pages show “Popular tracks”.
- **API endpoints**:
  - `GET /tracks/:trackId/plays` – returns `{ "count": 123 }` or similar.
  - `GET /artists/:artistId/popularity` – popularity metric based on track plays.
  - Or include `playCount`/`popularity` fields in existing responses:
    - `GET /tracks` / `GET /artists/:id/tracks`.
- **Data model**:
  - Simple: `play_counts(track_id, count)` updated by worker.
  - Or detailed: `track_plays(user_id, track_id, played_at)` + aggregates.
- **CV line**:  
  **"Implemented play-count and popularity analytics driven by SQS events and exposed via REST endpoints."**

> **After Phase 6 you add**: “event-driven analytics (queues + play-count features).”

## Phase 9 – Deeper Cloud (Lambda, API Gateway, Observability, OCI)

### 19. Lambda consumer + API Gateway

- **Goal**: Use **serverless** and deeper AWS services.
- **User story (operator)**:  
  *As an operator, I can see logs and metrics for my app and process play events using serverless functions.*
- **On screen**:
  - CloudWatch dashboards.
  - Logs for Lambda and API Gateway.
- **API endpoints**:
  - Existing `/play` can now publish to SQS or invoke API Gateway → Lambda instead of a long-running worker.
- **Components**:
  - **Lambda**:
    - Function that processes SQS messages and updates play counts.
  - **API Gateway**:
    - Fronts your API (or some subset).
  - **CloudWatch**:
    - Metrics, alarms (e.g. 5xx errors, DLQ depth).
- **OCI (optional)**:
  - Do a mini version of the above with OCI Functions, API Gateway, and Logging.
- **CV line**:  
  **"Built serverless components for a Spotify-like app using AWS Lambda, API Gateway, CloudWatch (and OCI equivalents) to process events and monitor the system."**
