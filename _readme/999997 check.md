# Node backend → cloud → microservices → expert (efficient order for interviews)

This plan is ordered so you learn **what interviewers and real-world jobs need first**: solid backend, then cloud, then architecture (monolith → microservices), then async (queues), analytics, open source, and UI. Each phase has a clear resume bullet.

---

## Key simplicity focus decisions

- **Simple and incremental** – One use case at a time; no big-bang.
- **Start with a monolith** – JOINs are fine; no message queues at first. Microservices come later (Phases 3–4).
- **Stack** – **MySQL**, **Express**, **React** (responsive). Framework switch (e.g. Express + Next.js) = separate repo, not this one.
- **Close backend first when needed** – Backend API without UI, without full DAL if useful; method-level APIs so the app shape is clear (Amos-style). Then add UI.
- **Workflow** – Pick use case → decide DB changes → decide endpoints → implement endpoints → **ask AI to implement UI**. Not waterfall; not too many docs.
- **DB** – Many work with the app locally and DB on cloud free tier (e.g. Atlas for Mongo). Here we use **MySQL installed locally**.
- **How to implement** – Use this plan and ask the agent to implement; use an execution template per endpoint (fill with AI, then ask AI to implement code).

## Phase 1: Backend foundation (Steps 1–8)

*Same as your current plan; summarized here so the full journey is in one place.*

1. **Docker** – API + MySQL in containers. **CV:** "Containerized Node API and MySQL with Docker Compose."
  - **Goal / by the end:** The app and DB run in containers; one command starts everything; no local MySQL install needed for others.
  - **User story:** *As a user, I can run the app the same way on any machine (or share it with others) so that "works on my machine" is no longer a problem.*
  - **On screen:** Same app as before; you run it via `docker-compose up` instead of `npm run dev` + local MySQL.

2. **Automated API tests** – Jest/Vitest + Supertest. **CV:** "Wrote integration tests for REST API using Jest and Supertest."
  - **Goal / by the end:** Code that calls your API (register, login, get likes) and asserts status/response; run with `npm test`.
  - **User story:** *As a user, I keep getting the same behavior (login, likes, search) after we change code so that nothing breaks silently.*
  - **On screen:** No UI change; you see test results in the terminal (pass/fail).

3. **Unified search + MySQL FULLTEXT** – `GET /search?q=&type=`, `searchable_entities` table. **CV:** "Designed unified search API backed by MySQL FULLTEXT."
  - **Goal / by the end:** One search endpoint that returns artists and songs (and optionally albums) from one query or table.
  - **User story:** *As a user, I can search for artists, albums, or everything in one search box so that I find what I want quickly.*
  - **On screen:** Search box shows results for both artists and tracks (e.g. sections "Artists" and "Songs").

4. **Transactions** – `DELETE /artists/:id` with cascade likes; optionally `DELETE /playlists/:id` with cascade tracks. **CV:** "Implemented transactional delete using MySQL transactions in Node."
  - **Goal / by the end:** Deleting an artist removes all likes atomically; deleting a playlist removes all its tracks atomically; no orphan rows.
  - **User story:** *As a user (or admin), when an artist is removed, my library no longer shows broken "likes". When I delete a playlist, all its tracks are removed so the app stays consistent.*
  - **On screen:** After delete artist, library no longer shows that artist's likes. After delete playlist, that playlist and its tracks are gone.

5. **Domain: albums + playlists** – Like album, album details + songs, create/rename playlist, add track to playlist. **CV:** "Extended REST API: albums, playlists, relational design."
  - **Goal / by the end:** User can like albums, open an album to see tracks, create/rename playlists, and add songs or a whole album to a playlist.
  - **User story:** *As a user, I can like albums, open an album to see its tracks, create and rename playlists, and add songs (or a whole album) to a playlist so that I can organize my music like in Spotify.*
  - **On screen:** Album and artist pages with song lists; "New playlist" and playlist list; "Add song" from artist or search; playlist shows its tracks.

6. **Elasticsearch** – Migrate search from MySQL FULLTEXT; same API. **CV:** "Migrated search to Elasticsearch; multi-entity search and indexing."
  - **Goal / by the end:** Search is powered by Elasticsearch; same request/response; better performance or matching at scale.
  - **User story:** *As a user, search stays fast and accurate even with lots of artists and albums so that I always get good results.*
  - **On screen:** Same search box and result layout; may feel faster or support better matching (e.g. typo tolerance).

7. **(Optional) MongoDB** – e.g. user preferences. **CV:** "Used MongoDB for [preferences] alongside MySQL."
  - **Goal / by the end:** One use case (e.g. user preferences) in MongoDB; API reads/writes it; MySQL stays source of truth for core data.
  - **User story:** *As a user, I can save preferences (e.g. theme, default view) so that the app remembers how I like it.*
  - **On screen:** e.g. Settings or profile where theme or default view is saved and restored.

8. **First cloud deploy** – PaaS or VM; managed MySQL (e.g. RDS). **CV:** "Deployed Node API and MySQL to [PaaS/cloud]; env-based config."
  - **Goal / by the end:** App is reachable on a public URL; DB is managed in the cloud; config via env vars.
  - **User story:** *As a user, I can use the app from anywhere (not only my laptop) so that it feels like a real product.*
  - **On screen:** You open the app in the browser via a URL; login and basic flows work.

**Rough total:** ~2–3 weeks. Stop here and you already have a strong backend + deploy story.

**Note on order:** Deploy is step 8 so you ship a feature-rich app. If you prefer to deploy earlier (e.g. right after Docker + tests), do step 8 as step 3 and shift the rest. If your DB doesn't yet have albums/songs, do step 5 (domain data) before step 3 (unified search) so search can return artists and songs from real data.

## Phase 2: Cloud fundamentals (AWS first, then OCI)

- **Goal / by the end:** You use AWS for config (Parameter Store), secrets (Secrets Manager or SSM for DB password, JWT), S3, RDS, SQS, SNS, CloudWatch; IAM roles so no keys in code; each tied to a Spotify-app scenario.
- **User story:** *As a user, I see album art from S3; the app runs on cloud; when I play a track it's recorded via SQS; I can get notified when an artist I follow releases (SNS).*
- **On screen:** Album art from S3; app reachable via cloud; play events flow to SQS (Phase 5 consumes them); optional "notify on new release" backed by SNS.

**Why now:** After Phase 1 you have something to run in the cloud. Learning cloud on a real app is more effective; AWS is the most requested in job posts. Config and secrets are critical in production; SQS/SNS are very common.

**What to learn (in order):**

1. **Concepts:** Regions, availability, IAM (users, roles, least privilege), networking (VPC basics). No deep dive yet—enough to use console and understand billing/region.
2. **AWS – config and secrets (critical):**
  - **How to read config** – Prefer **SSM Parameter Store** (or env vars) for non-secret config: DB host, port, S3 bucket name, SQS queue URL, feature flags. App loads at startup or on first use; env vars can override for local/dev.  
   **Spotify scenario:** API reads `DB_HOST`, `S3_BUCKET_ALBUM_ART`, `SQS_PLAY_EVENTS_QUEUE_URL` from Parameter Store (or env); no config in code.

  - **DB password and secrets** – Use **Secrets Manager** (or **Parameter Store SecureString**) for DB password, `JWT_SECRET`, API keys. App fetches via AWS SDK using IAM role; cache in memory; never log or put in env in repo.  
  **Spotify scenario:** On startup, Node API calls `SecretsManager.getSecretValue({ SecretId: 'spotify/db' })` (or SSM `GetParameter` with decryption); use returned credentials for MySQL and JWT signing. Rotate secret in console; app gets new value on next restart or refresh.

  - **IAM roles (no access keys in code)** – EC2, ECS, or Lambda gets temporary credentials via an **IAM role** attached to the resource; SDK picks them up automatically. No `AWS_ACCESS_KEY_ID` in env or code.  
   **Spotify scenario:** API runs on EC2/ECS with a role that has `secretsmanager:GetSecretValue`, `s3:GetObject/PutObject`, `sqs:SendMessage`; app never stores keys.

3. **AWS – popular services (tied to Spotify app):**
  - **S3** – Object storage. Upload album art (or profile pics); store URL in MySQL. Presigned URLs for private uploads if needed.  
   **Spotify scenario:** `POST /artists/:id/cover` uploads image to S3, saves `s3://bucket/artists/123/cover.jpg` URL in DB; client gets image URL from API.

  - **RDS** – Managed MySQL. Connect from API using host/port from Parameter Store and password from Secrets Manager.  
  **Spotify scenario:** Catalog, users, likes, playlists all in RDS; connection string from config + secret.

  - **SQS** – Message queue; producer sends, consumer processes async. Queue URL from Parameter Store.  
  **Spotify scenario:** When user presses "play," API sends `{ userId, trackId, playedAt }` to SQS; worker (or Lambda in Phase 9) consumes and updates `track_plays`. Keeps request fast and decouples analytics. *(Consumer/worker is built in Phase 5.)*

  - **SNS** – Pub/sub; fan-out to multiple subscribers (SQS, Lambda, email, push).  
  **Spotify scenario:** "New release from artist you follow." When a new album is added (or artist triggers "release"), publish to SNS topic `spotify/new-releases`; SQS subscription feeds a worker that updates a "releases" table or sends emails; optional Lambda to push to mobile. Or: "Notify me when artist X drops" → subscribe user to topic per artist.

  - **CloudWatch Logs** – Send app logs (stdout/stderr or SDK); query and set retention.  
  **Spotify scenario:** API and workers log to CloudWatch; filter by "playback error" or "DELETE /artists" for debugging and audit.

  - **CloudWatch Metrics / Alarms** – Custom metrics (e.g. plays/min, API latency); alarm when error rate or queue depth is high.  
  **Spotify scenario:** Emit `play_events_received` count; alarm if SQS dead-letter queue gets messages (failed play processing) or API 5xx spikes.

  - **EC2** (or **Lightsail**) – Run your Docker API if not using PaaS. Attach IAM role; read config and secrets at startup.  
  **Spotify scenario:** One small instance runs the Node API in Docker; role allows Secrets Manager, S3, SQS, Parameter Store.

  - **API Gateway** (optional here; deeper in Phase 9) – Single HTTP entry, throttling, API keys.  
  **Spotify scenario:** All client requests go through API Gateway → your API; rate limit per user or key to avoid abuse.

4. **Oracle Cloud (OCI) – second cloud:** Same ideas: region, IAM, Object Storage (like S3), MySQL HeatWave or standard MySQL, Compute, Vault (secrets). Do one small task: e.g. store one asset in OCI Object Storage from your app, or read a secret from Vault. **CV:** "Used AWS and OCI for storage, compute, and secrets; compared IAM and networking."

**Rough time:** 1–2 weeks (AWS focus) + a few days for OCI if you want multi-cloud.

## Phase 3: Stepping stone – modular monolith (before microservices)

- **Goal / by the end:** Code is split into clear domains (users, catalog, engagement); single HTTP entry; no cross-domain JOINs—catalog is called internally for data.
- **User story:** *As a user, the app behaves exactly the same (search, library, playlists) while we clean up the backend.*
- **On screen:** No visible change; same search, library, playlists. You are refactoring for a future split.

**Why now:** Interviewers ask "How would you break a monolith?" Doing a clean modular monolith first makes the split logical and teaches boundaries without operational complexity.

**What to do:**

1. **Module boundaries** – In your codebase, make domains explicit: e.g. `users` (auth, profile), `catalog` (artists, albums, tracks, search), `engagement` (likes, playlists, play events). Each module has its own routes, services, and **only touches its own tables** (or a clear facade). No `JOIN` from engagement to catalog tables; call a small internal "catalog client" or in-process API instead.

2. **API Gateway (concept first)** – Single entry point for all HTTP. Can be the same Express app with a single `app` and routers mounted by domain (e.g. `/api/users`, `/api/artists`, `/api/playlists`). Later this becomes a real gateway (e.g. AWS API Gateway or Kong) that routes to different services.

3. **Reduce joins across domains** – If "get my liked artists" today JOINs users → likes → artists, consider: store minimal data in engagement (e.g. `artist_id`) and fetch artist details from catalog when building the response. Prepares you for "each service owns its DB."

**Learning outcome:** "Refactored monolith into bounded modules and reduced cross-domain joins; prepared for service split." **CV:** "Structured Node monolith with clear domain boundaries and API gateway pattern."

**Rough time:** 3–5 days.

## Phase 4: Microservices – split and run

- **Goal / by the end:** Two or three separate services (e.g. auth, catalog, engagement), each with its own DB and Docker image; one gateway routes requests; app works the same for the user.
- **User story:** *As a user, the app still works the same (login, search, library, playlists) but now runs as separate services behind one URL.*
- **On screen:** Same app and URL; login, search, library, playlists all work. Only the backend architecture changed.

**Why now:** You have clear modules and no cross-domain joins; splitting is the next step.

**What to do:**

1. **Split into 2–3 services** – Example: (1) **auth-users** – register, login, JWT; (2) **catalog** – artists, albums, tracks, search (Elasticsearch); (3) **engagement** – likes, playlists, play events. Each has its **own DB** (or schema) and own repo or folder, own Docker image.

2. **Communication** – Sync: HTTP (catalog exposes `GET /artists/:id`, engagement calls it). Async: defer to Phase 5 (queue).

3. **API Gateway** – One entry for clients. Route `/api/auth/*` → auth-users, `/api/artists/*`, `/api/search/*` → catalog, `/api/me/likes/*`, `/api/me/playlists/*` → engagement. Can be simple reverse proxy (e.g. Nginx or Express proxy) or later AWS API Gateway / Kong.

4. **Run** – Docker Compose: gateway + auth-users + catalog + engagement + MySQL (or one DB per service) + Elasticsearch. Env: each service gets DB_*, and URLs of other services for HTTP calls.

**Learning outcome:** "Split monolith into 2–3 microservices with separate databases and API gateway routing." **CV:** "Migrated Node monolith to microservices; separate services for auth, catalog, and engagement; API gateway routing."

**Rough time:** 1–2 weeks.

## Phase 5: Message queues (why they exist + hands-on)

- **Goal / by the end:** When a track is "played," the API sends a message to a queue (e.g. SQS); a worker consumes it and updates play counts. No heavy write in the request path.
- **User story:** *As a user, when I press play, the app responds instantly and records the play in the background so playback never stutters.*
- **On screen:** Press play → immediate response; play is recorded in the background (counts show up after a short delay or on refresh).

**Why now:** You have services; queues give decoupling and async processing. Very common in interviews ("How do you handle high write load?" / "Async processing?").

**What they're for:** Decoupling producer (API that receives "song played") from consumer (worker that updates play counts). Reliability (retries, DLQ), scaling (many consumers), and avoiding one big transaction.

**What to do:**

1. **Concept:** Producer sends message (e.g. `{ userId, trackId, playedAt }`); consumer reads, processes, updates DB. No direct HTTP from API to analytics DB in the request path.

2. **AWS SQS** (or OCI Queue): Create a queue. API (or engagement service) sends a message when a track is "played"; a small Node worker (or Lambda) consumes, updates `track_plays` or similar. Use SDK in Node.

3. **In Docker:** Local dev: use ElasticMQ or LocalStack to emulate SQS, or a simple Redis list / Bull queue so the pattern is the same; for AWS, point to real SQS.

**Learning outcome:** "Used message queue (SQS) for async play-event processing; decoupled API from analytics updates." **CV:** "Integrated AWS SQS for asynchronous event processing in Node."

**Rough time:** 3–5 days.

## Phase 6: Analytics (Spotify-like: play counts, popularity)

- **Goal / by the end:** Play events (from queue or API) update play counts; API exposes play_count per track and popularity per artist; UI can show "X plays" and "Popular" lists.
- **User story:** *As a user, I see how many times a track has been played and which artists or tracks are most popular so I can discover what's trending.*
- **On screen:** Track rows or artist pages show play count or popularity; "Popular" or "Top tracks" sections use real play data.

**Why now:** You have (or will have) a queue for play events; analytics is the natural consumer and gives a concrete product feature.

**What to do:**

1. **Simple version first:** Table `track_plays` (user_id, track_id, played_at) or aggregated `play_counts` (track_id, count). On "play" (API or client call): increment or insert. Endpoints: e.g. `GET /tracks/:id/plays`, `GET /artists/:id/popularity` (aggregate from tracks), or include `play_count` / `popularity` in track/artist list responses.

2. **With queue (Phase 5):** API publishes "play" event to SQS; worker consumes and updates `track_plays` or `play_counts`. Same endpoints; updates are eventually consistent.

3. **Optional:** Simple dashboard or CSV export for "top tracks / artists" for learning; not required for resume.

**Learning outcome:** "Added play-count and popularity analytics; event-driven updates via message queue." **CV:** "Implemented play-count and artist popularity using event-driven updates (SQS + Node worker)."

**Rough time:** 2–4 days (simple) + already covered if you do Phase 5 with play events.

## Additional app features (later / optional)

The app is the vehicle for learning; these are extra Spotify-like features you can add **after** the main path if you want more product depth. Not required for the resume-focused plan.

- **Follow artist** – Notify when artist releases new music; or a "Following" list.
- **Share playlist** – Public link or share to social; optional visibility (public/private).
- **Recently played** – List of last N tracks or artists the user played (already partly covered if you have play events).
- **Shuffle / queue** – Playback queue (next up); shuffle mode. (Backend: persist queue or just session.)
- **Lyrics** – Show lyrics per track (third-party API or stored); backend endpoint that returns lyrics for a track.
- **Recommendations** – "Because you liked X" or similar; simple rule-based or later ML-style (e.g. co-likes).
- **Social** – See what friends are playing; follow friends. (Requires social graph and activity stream.)
- **Offline / download** – Mark playlist or album for offline; backend could track "downloaded" and license checks.

Pick one or two only if the app starts to interest you; otherwise stop when the learning goals for each phase are done.

## How this order helps you

  - **Queues** – Phase 5 explains what they're for and uses SQS with a concrete use case (play events).  
  - **Analytics** – Phase 6 gives Spotify-like play counts and popularity; ties to queues.  
  - **Monolith → microservices** – Phase 3 is the step in between (modules, API gateway, avoid joins); Phase 4 is the actual split.
